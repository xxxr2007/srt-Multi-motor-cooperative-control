# 7. 项目复盘：为什么到自动同步验证通过才算完成

> 本文依据本次真实对话与文件检查整理，隐去个人路径、仓库地址和测试标记。目标是让队友知道如何复现结果，以及哪些结论有证据支持。

## 目标与最终成果

用户希望把每次实质对话或项目结束后的关键内容，整理成图文笔记：陌生读者也能理解，正文精炼但覆盖主要信息；收尾时先询问，确认后保存，并能分享给队友使用。

最终打通了四个环节：

1. Codex 全局规则在收尾时提醒归档。
2. 可复用技能生成带摘要、流程图、关键决策和验证信息的笔记。
3. 独立 Obsidian 库保存笔记与索引，便于阅读和编辑。
4. 私人 GitHub 仓库保存版本，Git 插件完成自动提交与推送，并通过测试文件验收。

## 从“能写笔记”到“可日常使用”

第一版只包含技能、规则和安装说明。用户先预览了工作流笔记，再确认保存；这证明了生成与入库路径可用，却没有证明云端管理和自动同步。

讨论云端后发现 Obsidian 库是本地文件夹，云端同步需要额外配置。用户又希望把技能发给队友，于是制作了去除个人路径的分享包。

随后出现了一个实际问题：笔记库放在原项目文件夹中，新增笔记影响了原项目的 Git 状态。笔记经过校验后迁到独立库，最终放在用户指定的位置，与原项目平级；技能配置同步更新。

用户创建私人 GitHub 仓库后，先完成本地关联与初次提交。助手的远程查询曾出现连接重置，用户随后完成首次推送。这里要区分“已关联”“本地有提交”和“已上传”，不能混为一个状态。

## 自动同步配置中的易错点

用户安装 Git 插件，设置五分钟自动提交并同步。前三个概念需要解释：提交是记录本地版本，推送才是上传，拉取用于整合远程变化。

有几个选项不在 Automatic 页面，而在 Sync 页面：Push on commit-and-sync、Pull on commit-and-sync，以及 Pull on startup。本次通过读取已安装版本 2.41.1 的代码与配置确认位置，解决了“找不到后三项”的困惑。

插件出现选择远程仓库的窗口时，已有 `origin` 可选；这个界面是配置交互，不是错误提示。选择后仍要用实际远程结果验证成功，不能仅凭窗口消失判断。

## 验证证据

测试笔记在 2026-10-06 22:40:45（Asia/Hong_Kong）创建，包含唯一标记。助手没有执行任何提交或推送。

首次五分钟后的检查发现文件仍未跟踪，没有进入本地提交；一次进程检查未发现 Obsidian 运行，同时远程查询连接被重置。这个结果证明当时自动提交尚未完成，但不足以确定所有失败原因，也不能单凭网络错误断言云端内容不存在。

用户继续在 Obsidian 中处理远程选择后，后续检查发现：

- 测试文件进入了 22:47:33 的 `vault backup` 提交。
- 通过实时 GitHub 查询得到的分支提交号，与本地 HEAD 完全相同。
- 该提交的测试文件包含唯一标记。

这才构成“自动提交和上传已经生效”的证据。整个过程没有用助手的手动推送替代插件，因此保留了验证价值；但不能仅从这次成功推断在所有电脑、网络和关闭软件时都能同步。

## 可复用决策

| 决策 | 理由与影响 |
| --- | --- |
| 独立建库 | 避免混入研发项目的 Git 变更；可单独管理权限和历史 |
| 用户确认后归档 | 支持预览和跳过，避免把每轮聊天都变成笔记 |
| 技能与同步分工 | 技能负责内容，插件负责版本和上传，易于排查故障 |
| `.obsidian/` 默认不上传 | 避免本机布局和插件设置混入共享内容；队友需分别配置插件 |
| 唯一标记 + 实时远程验证 | 防止把已有文件、旧引用或本地提交误认成云端同步成功 |
| 分享包不绑定作者的路径和仓库 | 队友各自安装，支持个人知识库，也可另行协作 |

## 尚需持续注意的事项

收尾提醒是模型指令，不是关闭窗口事件。长项目和多聊天总结仍可能需要补充来源。Obsidian 必须运行才能执行插件定时任务；冲突、网络和登录问题需要处理。多人编辑同一笔记时，应先同步再编辑，发生冲突时检查两端内容。

因此，本包的完成标准不是“已经安装”：**队友应独立完成一轮生成笔记、预览确认、保存、自动提交和远程内容核对。**
