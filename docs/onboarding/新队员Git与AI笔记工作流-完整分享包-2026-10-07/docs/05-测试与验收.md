# 5. 测试与验收：证明它真的自动上传

## 为什么要创建新的测试笔记

手动点 Commit-and-sync 成功，只证明插件能执行同步。创建新文件后不手动干预，才可以测试定时机制是否可用。

测试时只改笔记，**不要手动执行 git add、commit、push 或 Commit-and-sync**。否则无法判断是谁完成上传。

## Windows 辅助脚本

在分享包根目录运行：

```powershell
.\scripts\create-sync-test.ps1 -VaultPath 'D:\Obsidian\AI项目知识库'
```

脚本打印一个唯一标记和笔记的 Git 相对路径，记录下来。它只创建本地文件，不提交、推送或添加索引。

1. 保持 Obsidian 打开**这个库**，确认 Git 插件启用且间隔为 5。
2. 记录创建时间，等待约五分钟。
3. 把刚才输出的相对路径和标记原样代入：

```powershell
.\scripts\verify-sync-test.ps1 `
  -VaultPath 'D:\Obsidian\AI项目知识库' `
  -RelativePath 'AI 项目笔记/2026/实际生成的文件名.md' `
  -Marker '实际生成的唯一标记'
```

如 Git 未在 PATH，但知道其安装路径，给验证脚本增加 `-GitPath 'C:\Program Files\Git\cmd\git.exe'`。

验证脚本不提交、不推送、不修改原仓库；查询实时远程分支，再检查那个提交里的文件标记。它不会以旧的 origin/main 引用代替实时远程状态。

| 输出 | 结论 |
| --- | --- |
| NOT_COMMITTED | 标记还没有进入本地 HEAD，自动提交阶段尚未完成 |
| NOT_ON_REMOTE | 实时远程提交可读，但不存在这个文件或标记 |
| SYNC_VERIFIED | 实时远程提交包含测试标记，上传得到验证 |
| UNVERIFIED | 网络、认证或本地缺少远程提交对象，无法得出结论 |

UNVERIFIED 不是“不存在于云端”。如果云端提交对象尚未在本地，直接在 GitHub 打开文件核对标记，或请助手在隔离临时仓库获取远程内容检查，不要为了测试而干扰插件正在执行的同步。

## 不运行脚本也能验收

新建一篇笔记，写入日期和随机字符串，等待后做两项检查：

- **本地：**`git status --short` 中该文件不再是 `??`；用 `git log -1 -- '笔记相对路径'` 查看提交记录。仅状态干净仍不足以证明上传。
- **云端：**在 GitHub 页面刷新相应分支，打开文件并核对随机字符串；核对提交时间与说明。

## 测试成功之后

正常使用时由 Codex 生成项目笔记，Obsidian 阅读和编辑，插件上传。每次看到异常提示时查看同步状态，不需要每个项目重新搭建一遍。

测试笔记可以保留作为验收记录。要清理时删除它，插件会把删除也记录并同步；删除当前文件并不会抹去 Git 历史中的版本。

本包脚本不会自动安排提醒、持续监控或创建系统后台任务。五分钟等待可以自己计时，或明确让助手在本轮等待并检查；若使用定时自动化，应确认实际创建成功再结束任务。
