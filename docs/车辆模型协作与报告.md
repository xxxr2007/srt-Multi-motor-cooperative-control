# 查看我和队友分别改了什么

每个工作区只维护当前文件。工具从 Git / Git LFS 自动取出共同旧版，分别比较“共同旧版 → 我”和“共同旧版 → 队友”。生成的快照和报告放在已忽略的 results/model-review/ 中，不需要人为维护旧模型副本。

## 本机使用

1. 每名成员首次在自己的克隆目录双击 `配置车辆协作工具.cmd`。需要 Python 3.10+、Git LFS 和 MATLAB；当前已验证安装版本为 R2024b。配置只作用于当前仓库，不修改全局 Git 配置。
2. 双击 `查看我和队友的改动.cmd`，选择队友分支编号。工具先 fetch 更新远端分支，不 pull、不覆盖工作区，也不执行合并。
3. 浏览器自动打开 `index.html`。分别展开“我的改动”和“队友的改动”，看新增文件、结构路径、属性旧值/新值及 M 文件逐行改动；点链接可看 MATLAB 原生完整报告。
4. 同一文件被双方修改会单列提示。该提示不是冲突判定，实际冲突由合并工具判断。

“我”默认是本地已保存的文件，包括未提交修改；MATLAB 编辑器里未保存的内容不在磁盘，需先保存。“队友”是选择的分支，并不自动等于某一个作者。报告准确记录双方 ref、commit 和共同旧版。

命令行等价操作：

```powershell
python tools/model_review/run_review.py --theirs origin/队友分支
```

完整控制比较版本：

```powershell
python tools/model_review/review.py --mine HEAD --theirs origin/队友分支 --matlab "C:/Program Files/MATLAB/R2024b/bin/matlab.exe"
```

默认检查 electrical/simulink 内的 .slx、.mdl、.m、.sldd；其他目录用 `--scope 目录` 指定，可重复。没有共同祖先会报错，不会猜测基线；需要人工选定基线时可加 `--base 提交号`。未运行 MATLAB 时仍能生成结构清单，页面会明确标注原生报告尚未生成。

## GitHub 自动报告

PR 修改车辆仿真目录、报告工具或工作流时，会运行 `Vehicle model review`。PR 的“我”指目标分支，“队友”指提交 PR 的源分支，双方都分别与共同祖先比较。因此即使目标分支也有新修改，也能单独审查提交者的改动。

在 PR → Checks → Vehicle model review → Details，查看运行摘要；到该次 Actions 的 Artifacts 下载 `vehicle-model-review-*`，完整解压后打开 `index.html`。HTML 不能直接在 GitHub Artifacts 页面渲染，需下载打开。原生报告和总览一起打包，保留 30 天。

也可到 Actions → Vehicle model review → Run workflow，分别选择 mine、theirs 的分支或提交。云端没有本机未提交修改。

工作流使用 GitHub 托管 Ubuntu + MATLAB R2024b，公开仓库可用 MathWorks actions 的公开项目许可；如果将仓库改为私有，需要配置相应 MATLAB 批处理许可。第三方库必须另外提供；缺失时会显示导出警告或让原生报告步骤失败，同时保留已生成的结构报告。报告生成不会运行车辆仿真或宣称测试通过。

## 双方都改了同一模型

本仓库车辆目录的 SLX 继续使用 LFS 保存。自定义合并适配器先还原 LFS 内容，再交给 MATLAB 自动合并，成功后重新写入 LFS 对象。自动合并失败时保留原始输入并交由 Git 标记冲突。

每人开始前都需要执行本机配置脚本。冲突后可以执行：

```powershell
git mergetool -t mlMerge -- electrical/simulink/整车仿真模型/simulink14dof.slx
```

原生工具中查看 Base / Mine / Theirs，选择冲突项并保存。非冲突改动自动合并也应审阅，最终应运行相应车辆仿真工况。Git 差异比较可用：

```powershell
git difftool -t mlDiff HEAD -- electrical/simulink/整车仿真模型/simulink14dof.slx
```

## 实际修改说明怎么写

开 PR 时会自动出现模板。自动报告提供可复核的路径和旧值/新值；修改人补充目的、接口影响、工况和结果。不要把结构重组造成的路径新增直接写成新增物理功能，也不要把尚未验证的效果写成已通过。

例如：`修改 Subsystem2/控制器的 Kp：10 → 12；目的是降低固定工况的横向误差；已按同一路径、同一初速运行 12 s，结果见日志 X。` 其中数字和结果必须来自实际修改与验证，不能照抄示例。

参考 [实际模型报告填写示例](实际模型报告填写示例.md)。PR 模板还包含“队友已有改动与本次集成”，用于区分贡献来源。

## 自动清单的边界

结构摘要按模块路径比较，额外用相同 SID、名称和类型标注可能移动的节点；这是辅助线索，最终结合 MATLAB 原生比较判断。连线、模型配置、Stateflow/MATLAB Function 代码等完整变化查看原生报告。外部 .m 文件单独逐行比较。目录外的依赖需扩大 --scope，不能默认报告已覆盖。

本次生成报告时，E 盘的 simulink14dof01.slx 尚未纳入 GitHub 仓库，因此默认报告不包含它。先在任务分支中放入需要协作的模型及依赖文件，后续才会自动覆盖这些修改。
