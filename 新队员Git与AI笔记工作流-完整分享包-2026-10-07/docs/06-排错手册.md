# 6. 排错手册

先判断故障在哪一层：**生成笔记 → 保存文件 → 本地提交 → 云端推送 → 其他设备拉取**。这样不会把文件写入问题当成网络问题，也不会把本地提交成功当成云端成功。

## 这次真实遇到的情况

| 现象 | 实际发现 | 处理方法 |
| --- | --- | --- |
| 新增笔记影响原项目 Git 状态 | 笔记库最初位于原项目里；笔记未跟踪 | 迁到独立库，校验文件后移除原笔记目录，更新安装后的技能路径 |
| `Recv failure: Connection was reset` | GitHub 只读查询连接失败 | 区分无法访问与内容不存在；检查网络、代理及登录后重试，不删除仓库或强推 |
| 找不到后三个同步设置 | 查找的页面不对；已安装版本实际包含选项 | 进入 Git → Sync；Pull 与 Commit-and-sync 分组分别有对应选项 |
| 弹出“选择或创建远程仓库” | 已有 origin 可选择 | 选 origin，核对自己的仓库地址；这是交互提示，不是报错 |
| 创建测试笔记五分钟后仍没提交 | 文件仍为 `??`；一次进程检查未发现 Obsidian 运行 | 检查软件、库、插件及提示；这条证据不足以断言全部原因 |
| 后续同步成功 | 本地和实时远程提交一致，测试标记存在 | 至此确认插件执行了提交和上传；测试期间助手没有手动提交或推送 |

## 1. 技能保存失败或写错位置

检查已安装的 `skills/obsidian-project-notes/settings.json`，而不是分享包副本。库路径应存在且是你当前希望使用的独立库。

如果系统拒绝工作区之外的写入，应按正常审批申请准确路径的权限，不绕过限制；没有写入成功时只能说草稿已生成，不能说“已保存”。

升级报“already installed”时使用 `-Update`，或按手动升级步骤保留个人配置。全局规则没有生效时检查非空 AGENTS.override.md 是否优先、新聊天是否加载、项目规则是否覆盖。

## 2. Git 插件找不到 Git，或 Git is not ready

确认 `git --version` 能执行，安装的是完整 Git；安装后重启 Obsidian。库根目录应是正确 Git 仓库，Advanced 中的库路径没有指向其他项目。

如果 Obsidian 找不到终端里能用的 Git，可在插件设置中指定实际 Git 可执行文件路径。不要照抄别人机器上的用户名目录。

## 3. 五分钟后仍是未跟踪文件 `??`

依次确认：

1. Obsidian 正在运行，左下角显示正确的独立库。
2. 社区插件中的 Git 已启用。
3. 自动提交间隔不为 0，“only staged files”关闭。
4. 自定义提交消息提示关闭，远程选择或登录窗口没有停在等待输入。
5. 插件通知、Source Control 和控制台是否显示 Git、身份或网络错误。

如果“停止编辑后同步”开启，持续编辑可能推迟触发。文件被 .gitignore 忽略时不会被纳入提交，可用 `git check-ignore -v -- '相对路径'` 查规则。

手动 Commit-and-sync 可以用于诊断；完成后再建一个新测试文件、重新计时，才能重新验证自动机制。

## 4. 已有本地提交，云端却没有文件

检查 `git remote -v`、`git branch -vv` 和插件 Push on commit-and-sync 开关。分支需要跟踪正确的远程分支，账号需要有仓库写入权限。

首次登录通过 Git Credential Manager 或已配置的 SSH 完成。[认证说明](https://publish.obsidian.md/git-doc/Authentication)

连接重置、超时或无法解析地址属于连接问题的表现，不能仅据此判断仓库不存在、密码错误或插件设置错误。先在同一电脑验证网络与终端访问，记录原始错误，再针对原因处理。

## 5. `remote origin already exists`

查看 `git remote get-url origin`。地址正确时不用再添加；地址错误时先确认目标和权限，再修改连接。这个错误不要求重新初始化整个库。

## 6. `non-fast-forward`、`unrelated histories` 或合并冲突

远程已经有提交或不同设备都修改了内容。先查看两端历史，拉取并整合；冲突文件需人工判断保留哪些内容。

远程预置了 README 时按“先克隆再复制笔记”接入。不要默认强推、硬重置或直接丢弃一端的笔记。

## 7. 明明已上传，另一台电脑没有更新

GitHub 收到提交后，另一台电脑仍需拉取。确认仓库和分支一致，启用该设备的 Pull on startup 或手动 pull。`.obsidian/` 被忽略时，插件安装与设置不会跟随仓库下载，需要在每台设备配置。

## 8. 自动检查未成功安排

本次尝试单次调度时遇到“no future runs”和 DTSTART 参数限制，最后改为本轮直接等待，再实际检查。这是助手的调度问题，与 Git 插件是否同步是两回事。

让助手“稍后检查”时，应确认它确实创建了可运行的检查，或者仍在等待。不要把一句“已安排”当成自动化已经存在。本包通过手动计时/明确等待测试，不依赖特定 Codex 调度语法。

## 9. Windows 的 LF / CRLF 警告

提交时出现“LF will be replaced by CRLF”通常是换行符转换提示，不等于提交失败。查看 Git 返回结果和提交是否生成；团队如需统一换行，再共同制定 .gitattributes，不为消除提示而修改其他项目的全局配置。

## 向队友或助手提供什么信息

提供插件版本、原始错误文字、当前库路径、当前分支、`git status --short` 和 `git branch -vv`，说明问题发生在提交、推送还是拉取。仓库地址中若带凭据应先去掉；不要提供密码、令牌或私钥。
